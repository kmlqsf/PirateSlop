## Правила приёмки

- Бюджет кадра 8.33 мс; цель P99 ≤8.33 мс, основная работа CPU/GPU около 7 мс. CPU и GPU не складываются.
- Попадания: цель ≤16.67 мс; систематические кадры >33.33 мс неприемлемы.
- После этапа: три одинаковых benchmark-запуска и проверка изменённой механики. Прирост должен превышать разброс повторений; разница <5%, укладывающаяся в шум, предварительная.
- Итоговая проверка: Release без подключённого Profiler, 15 минут боя, второй клиент, позднее подключение, целый/повреждённый/отремонтированный корабль, оптика.
- Полный флот 10 кораблей — отдельный стресс-тест. Синтетические участники не эмулируют реальные сетевые соединения.
- Первый запуск процесса и повторные запуски сравниваются отдельно. Разрешение, render scale, качество, FOV, маршрут и состав должны совпадать.
- Статусы: Запланировано; В работе; Реализовано — ожидает проверки; Проверено; Отложено. Компиляция не подтверждает игровой FPS или сетевую корректность.

## Benchmark

Основной запуск: главное меню → Диагностика → Тест производительности, доступен и в Release. F4 не назначается.

Свежая локальная тестовая сессия: четыре корабля, 12 синтетических персонажей без AI, фиксированный профиль, 30 секунд подготовки после готовности. Пролёт: корабль30с, флот35с, все13ивентов85с, океан/водоворот35с, шторм40с, подводный участок15с. Итого240с измерения. Маршрут хранится в Resources/Performance/BenchmarkRoute.json и версионируется.

В мире также есть торговый корабль кормового ивента. Проверка состава считает четыре корабля экипажей отдельно; JSON ships учитывает все суда, crewShips — только суда команд. Торговцу сохраняется штатное движение. Число12 означает синтетических персонажей, не сетевые соединения. Радиус шторма3000м, день, волны1/1/1, стартовая фаза волн0. Пауза зоны сохраняет её визуал и исключает урон зоны. Физика не является битово детерминированным replay; нужны повторные замеры.

JSON — полный отчёт с покадровыми данными; TXT — краткая сводка. Папка Application.persistentDataPath/PerformanceReports. Недоступные счётчики обозначаются N/A (в числовых массивах JSON -1, с описанием доступности). INVALID означает нарушение условий, CANCELLED — отмену. Эти результаты не принимаются как baseline.

Начиная с формата отчёта v2 JSON и TXT содержат посекундную шкалу `seconds`, название участка, средний FPS, P99/max, CPU/render/GPU и выделения GC. Для каждого интервала указаны индексы кадров и самый долгий кадр. Каждый кадр сохраняет позицию и quaternion камеры, готовность зоны, радиус, расстояние до границы (положительное — безопасная сторона), интенсивность дождя и погружение по состоянию rain controller. `rainReady=false` означает отсутствие данных этой системы, а не доказанное отсутствие дождя. Интервалы группируются по времени начала кадра и участку; длинный кадр целиком относится к своей начальной секунде. Первый/последний интервалы могут быть неполными. Старые отчёты v1 требуется записать повторно для штатного сравнения.

Текущий формат v3 добавляет `cpuStageNames/cpuStageMilliseconds`. Исходный `instrumentationVersion=wallclock-v1` имел30категорий; `wallclock-v2` —39; текущий `wallclock-v3` —40: дополнительно измеряется ShipHullProxySetup. В разбивке есть руль, плавучесть, проверки мира, ограничение корпуса, широкая/точная проверки, casts, sync и запись Transform. Stopwatch на основном потоке измеряет корневые фазы PlayerLoop, отдельные физические/анимационные/рендерные узлы, симуляцию и публикацию кораблей/персонажей, перенос пассажира/Physics.SyncTransforms/motor/support, обновление телеметрии и сам сборщик. Эти времена доступны и без включённого Profiler; они включают ожидания и вытеснение потока. Вложенные интервалы перекрываются, складывать их нельзя. Повторные FixedUpdate суммируются. Показатели выводятся по всем кадрам, участкам и для длинных кадров. Отсутствующий GC allocation counter теперь даёт N/A и `gcMeasuredFrames=0`, а не ложный ноль байт.

Датчики PlayerLoop добавляются только на время подготовки/записи, без изменения порядка исходных узлов или шага симуляции. При освобождении удаляются только собственные датчики, остальные системы сохраняются. Буферы выделяются заранее; стоимость нового измерителя в Player ещё предстоит проверить. Сравнение поддерживает v2 и v3, но разные schema/instrumentationVersion отмечает как несопоставимые. Текущий маршрут `test-map-v2` меняет только последние15с: координаты вынесены за пределы радиуса воронки500м. Для COMPLETE необходимо записать минимум10с фактического погружения по rain controller.

В главном меню диагностики есть переключатель «Быстрая проверка пути корпуса», по умолчанию включён. Это оптимизация эквивалентного расчёта, не уровень графики. `metadata.hullSweepFastPath` записывает выбор; изменение во время benchmark даёт INVALID. Для контролируемого A/B в одной версии измерителя можно выключить переключатель до запуска и сравнить со включённым. Сравнение явно показывает это разрешённое отличие оптимизации, остальные условия проверяются штатно; first/repeat warmState должны совпадать (для двух первых запусков перезапустить Player между ними).

Полная погода обязательна для текущего эталона: зона, небо с объёмными облаками, штормовой дым, дождь с экранными эффектами и молнии. Подводный renderer также проверяется. Перед измерением и после него проверяются компоненты, активные renderer features выбранной камеры, фиксированный радиус и параметры окружения; отключённый обязательный компонент или изменившаяся конфигурация даёт INVALID. Состояние features и основные параметры погоды сохраняются в `environmentSignature` и участвуют в сравнении. Это проверка подключения, не подтверждение корректного внешнего вида каждого эффекта.

Обычный тест нагрузки на процедурной карте уже запускает зону и штатную погоду этой карты с приостановленным сужением. Торговые суда ивентов исключены из количества кораблей экипажей и управления синтетическим флотом в обоих режимах; их штатные эффекты и движение сохраняются. Этот режим с десятью кораблями остаётся отдельным стресс-тестом, его ракурсы не заменяют фиксированный benchmark.

Во время измерения Player потеря фокуса окна, смена разрешения/качества/лимитов/FOV/render scale, ошибки или неполный состав делают результат INVALID. В Editor потеря фокуса отдельно не блокирует тест. Escape сохраняет CANCELLED. Отмена и завершение отключают локальный хост, освобождают тестовый мир и возвращают меню. Запуск во время другой сессии не допускается. Сохранение и сравнение выполняются в фоне; raw-буфер заранее выделен, его размер записан в JSON.

В метаданных: железо, версия/тип сборки, Unity/API/pipeline, настройки, карта/маршрут, роль, состав, startup/warm state. Метрики: средний FPS; 1%low=1000/среднее медленного1%кадров; P50/P95/P99/P99.9/max; кадры >8.33/16.67/33.33/50/100мс; CPU main/render/GPU; draw calls/SetPass/triangles; GC/память; метки; состав/эффекты/обломки; physics/network steps; события и ошибки.

Пролёт не включает автоматический бой. Ручная запись доступна из диагностики в текущей игре. Серия: первый удар,10повторных,новыйкорабль,нелетальныепопадания,смерть,групповоеразрушение,ремонт,повторныйудар.

Сохранять графику пользователя. Balanced ещё не создан: начальный baseline выполняется на существующем PC с render scale1; после этапа7 формируется отдельная серия Balanced. Не выдавать PC за Balanced.

### Запуск первой серии пользователем

1. Для конечных замеров собрать Windows Build → Release. Выход: Builds/WindowsRelease/PirateSlop.exe. Прежний Windows Build → Build остаётся Development и пишет Builds/Windows.
2. Выбрать QHD, PC, отключить VSync; проверять параметры в отчёте. Не менять настройки между сравниваемыми запусками.
3. Главное меню → Диагностика → Тест производительности. Сейчас сначала нужен один диагностический запуск новой сборки с отчётом v3/test-map-v2 для выяснения причины8FPS; три baseline-запуска — после устранения/объяснения этой проблемы. Проверить, что маршрут видит корабль, все ивенты, шторм и воду. Окно Player держать в фокусе.
4. Диагностика → Открыть папку отчётов. Передать JSON+TXT всех запусков. Первый benchmark процесса помечен отдельно от повторных; кэши могли быть прогреты прежней игрой.
5. Кнопка Сравнить последние два теста сравнивает последние два COMPLETE benchmark и сохраняет comparison-*.txt. Несовпадения условий выводятся явно; первая и повторная серия процесса несопоставимы автоматически.
6. Для попаданий использовать Development-сборку: создать тестовую игру, меню паузы → Диагностика → Запись игры и попаданий, вернуться на палубу, выполнить серию, остановить запись в том же меню. Дополнительно сохранить короткий CPU Timeline из Player Profiler без Deep Profiling.

Для анализа выбранной пары из корня проекта: python Tools/Performance/compare_reports.py BEFORE.json AFTER.json --output COMPARISON.txt. Код возврата2 означает несопоставимые условия.

### Как устанавливаем причину просадки

1. В TXT найти проблемную секунду/участок и самый долгий кадр. По JSON `frames`, `seconds`, координатам и направлению камеры связать его с маршрутом; события связывать по `unityFrame` и времени. Это описание ракурса, а не снимок пикселей или список гарантированно видимых объектов.
2. Разделить постоянную нагрузку и одиночный фриз. Сопоставить GPU, CPU main/render, GC, шаги физики и метки. Для самых долгих кадров TXT выводит доступные метки ≥0.05 мс. CPU frame time с ожиданием GPU сам по себе не доказывает загрузку игровой логики. Недоступные GPU/markers требуют отдельного профиля, их нельзя трактовать как нулевую стоимость.
3. Воспроизвести нужные секунды в Development с CPU/GPU Timeline без Deep Profiling. Проверить проходы облаков/дыма/воды/теней и конкретные вызовы физики/разрушения/создания объектов. Итоговые FPS подтверждать отдельным Release без Profiler.
4. Проверять гипотезу контролируемой серией A/B/A: полный эффект → отключён один подозреваемый визуальный проход → полный эффект. Сохранять маршрут, seed, настройки, состав и прогрев; по три повтора каждого варианта. Изменение frame time должно превышать разброс, а возврат эффекта — воспроизводить затраты. В «Настройки → Графика» сравнивает включённую/выключенную «Оптимизацию облаков и зоны», вид снаружи/внутри шторма, облака, оптику и управление кораблём/кабестаном. Автоматический пролёт для этой проверки не нужен. Попадания поставлены на паузу и не являются текущим поручением пользователю. После игрового отзыва — оставшийся CPU/геометрия/качество и новый Release-control с зафиксированным CloudQuality. Стресс SyncTransforms,120FPS/P99,полноценные пресеты,длительная сессия и второй клиент остаются открытыми.
