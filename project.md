Канаты парусов, 2026-09-16: вместо колеса мыши у мачт — стойка SailRopeRack рядом со штурвалом, четыре каната по числу существующих парусов. ЛКМ захватывает рукоять; движение мышью вниз расправляет связанный парус, вверх собирает, отпускание сохраняет долю 0–100%. Каждый исправный парус даёт 25% полной тяги; структурные повреждения уменьшают вклад без перенормирования оставшихся парусов. На время захвата блокируются ходьба, обзор и использование предметов. Сервер хранит независимые натяжения и занятость; разные игроки могут тянуть разные канаты, смерть/дистанция/отключение/таймаут освобождают захват. HUD в существующем стиле показывает четыре шкалы, выбранный канат, занятость, повреждения, общую тягу и скорость; у штурвала видна сводка. Повторная подготовка: PirateSlop > Configure Sail Ropes. ProtocolVersion=93. Игровую, визуальную и сетевую приёмку выполняет пользователь.

## Игра и MVP

Процедурная карта V1, 2026-09-07: в SampleScene и NetworkOcean подключён ProceduralWorld. Каталог из шести форм островов/рифов/скал, seed, точки расширения и JSON-карты. Цель текущего MVP — сетевая дуэль на пиратских кораблях: два игрока с разных ПК подключаются к одной сессии, каждый управляет своим кораблём и может стрелять по кораблю другого игрока. Долгосрочная идея battle royale может обсуждаться позже, но сейчас не является требованием MVP. Игровой ориентир по ощущениям совместного управления и морского боя — Sea of Thieves. How to Fish используется только как визуальный референс для создания моделей и ничего больше: не копировать материалы, механики, UI, настроение страницы магазина или игровые правила. Подтверждённый визуальный референс: [How to Fish](https://store.steampowered.com/app/4001890/How_to_Fish/). Перед художественной работой изучить изображения игры по этой ссылке.

MVP: два корабля и два реальных игрока. Игроки с разных ПК подключаются через интернет к одной сессии; каждый игрок управляет своим кораблём и может стрелять по кораблю другого игрока. Поддержка только localhost или локальной сети не удовлетворяет MVP:

- два корабля — по одному управляемому кораблю на игрока;
- штурвал — управление своим кораблём;
- пушки — стрельба по кораблю другого игрока;
- урон корабля — наблюдаемое состояние, одинаковое для обоих игроков.

Боты, battle royale-цикл, сужение зоны, матчмейкинг, прогрессия, экономика и большой онлайн не входят в согласованный MVP. Не добавлять их в текущую задачу без отдельного запроса. Победу, затопление, возрождение и правила окончания тестовой сессии уточнять при реализации соответствующего этапа.

## Работа ИИ

Пользователь описывает результат, ИИ выполняет доступную работу целиком: код, объекты, компоненты, ссылки, модели, импорт, префабы и сохранение. Ожидаемая передача пользователю — открыть указанную сцену, запустить и проверить, без ручного навешивания скриптов.

Обычные действия внутри задачи выполнять самостоятельно. Уточнять только существенную неопределённость, влияющую на результат, или недостающее разрешение. Не считать широкое разрешение на работу разрешением на коммит и push: для них действует отдельное правило ниже.

Перед изменениями прочитать нужные инструкции и существующую реализацию. Сохранять чужие незавершённые изменения. Не переделывать несвязанные системы. Если инструмент или редактор недоступен, выполнить независимую часть и точно назвать оставшийся шаг; не заявлять, что сцена настроена или проверена без подтверждения.

Документация и ответы — по-русски. Код, имена файлов и объектов — по-английски. Обновлять эти документы при изменении фактической архитектуры и согласованных решений. Не записывать предложения как принятые решения.

## Совместная работа и Git

Два разработчика работают над всеми частями проекта по очереди и передают результат через GitHub. Рабочую ветку определять по репозиторию и текущей договорённости, не предполагать её имя.

1. В начале проверить корень репозитория, `git status`, ветку и remote. При доступной сети получить состояние remote через fetch.
2. Если рабочая копия чистая, обновить согласованную ветку через `git pull --ff-only`. Если есть локальные изменения или расхождение истории, сохранить их и разобраться; не применять автоматический reset, clean, stash или force push.
3. На время передачи не редактировать одни и те же сцены, префабы и бинарные модели на двух ПК. Git сам по себе не обеспечивает такую блокировку.
4. Перед публикацией сохранить редакторы, проверить diff, перечислить изменённое, выполненные проверки и оставшиеся ограничения. Предложить конкретный коммит и целевую ветку.
5. **Создавать коммиты и выполнять push только после явного подтверждения в чате.** Одно подтверждение может разрешать оба действия для описанного набора изменений. Подтверждение только коммита не разрешает push. Не считать подтверждение бессрочным для будущих задач.
6. После разрешения включить только относящиеся к задаче файлы, выполнить коммит и push, сообщить хеш и результат отправки. При конфликте с новым push друга не перезаписывать remote.

Сохранять `.meta` вместе с Unity-ассетами; переносить ассеты с сохранением GUID. Не коммитить `Library`, `Temp`, `Logs`, `UserSettings`, локальные токены и настройки соединений. Соблюдать имеющиеся `.gitignore` и `.gitattributes`: FBX, BLEND и многие другие бинарные ассеты уже используют Git LFS. На обоих ПК проверять, что скачаны реальные LFS-файлы.

Для каждой задачи дать короткие шаги проверки и ожидаемый результат; ясно отделить выполненное от непроверенного. Не вводить обязательный большой набор автотестов без необходимости.

Критерии MVP: два клиента с разных ПК через интернет участвуют в одной сессии; каждый игрок находится на своём корабле, управляет им через штурвал и стреляет из пушек; попадания и урон видны обоим игрокам одинаково; выход игрока и освобождение управления корректно синхронизированы.

## Версия игры на экране

В нижнем правом углу меню и игры автоматически отображается `v<major>.<minor>.<число коммитов> · <короткий hash>`. Например, v0.1.36 · c481b663. Major/minor берутся из PlayerSettings.bundleVersion; номер ревизии и hash — из текущего HEAD. Это версия отображения игры, независимая от сетевого ProtocolVersion; bundleVersion автоматически не переписывается.

При локальных незакоммиченных изменениях добавляется +dev. При shallow clone добавляется (shallow): число коммитов в таком клоне неполное, точный идентификатор — hash. При недоступном Git показывается unknown, старый штамп не используется как актуальный.

Штамп пересчитывается при загрузке Editor-скриптов, перед Play Mode и перед сборкой; вручную — PirateSlop → Refresh Game Version. Во время уже запущенной игры версия фиксирована. Сборка содержит свой штамп и не требует Git на компьютере игрока. Для одинаковых номеров ревизий использовать полный клон репозитория. Amend может сохранить число коммитов, но изменит hash.

GameVersionOverlay создаётся автоматически, сохраняется между сценами. GeneratedGameVersion.txt и его .meta игнорируются Git, чтобы обновление штампа само не помечало рабочую копию изменённой. Коммит-хуки и ручное повышение patch не требуются. Компиляция и создание штампа проверяются отдельно от отображения в Play Mode; визуальную приёмку выполняет пользователь.
