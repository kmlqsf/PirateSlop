# Инструкции ИИ для PirateSlop

## Режим работы по умолчанию

Эти правила уточняют и заменяют противоречащие им требования к объёму работы и проверкам в `project.md`, `unity.md` и `blender.md`. Инструкции более высокого приоритета сохраняют силу.

- Экономить токены: выполнять только основную логику и минимальные изменения по запросу.
- По умолчанию не запускать билды, тесты, игровые/визуальные проверки и дополнительные диагностические прогоны. Пользователь проверяет результат сам и сообщает об ошибках. Запускать такие проверки только по явному запросу либо если этого требует инструкция более высокого приоритета. Исключения: для моделей Gemini и агентов Antigravity самостоятельная компиляция для проверки кода на ошибки является обязательной.
- Не расширять задачу дополнительной полировкой, отчётами и несвязанными исправлениями. Читать лишь необходимый для изменения контекст.
- В конце кратко сообщать, что изменено и что пользователю проверить самому. Не заявлять об успешных проверках, если они не выполнялись.
- Отвечать кратко, без длинных планов и повторяющихся обновлений.
- Прозрачность ошибок: если субагент сталкивается с системной проблемой (зависание, отвал MCP), он обязан сразу прервать работу и вернуть отчет об ошибке главному агенту для передачи пользователю, без бесконечных попыток починки.
- Самообучение (Автоматические уроки): Если пользователь исправляет твою ошибку или указывает на неверный подход, ты обязан самостоятельно проанализировать ошибку и записать краткое правило в файл `lessons.md` в корне проекта, чтобы не допускать её в будущем. Перед началом любой новой задачи всегда читай `lessons.md`.

## Контекст проекта

Для короткого отчёта по конкретному объекту или префабу Unity используй `PirateSlop.Editor.FocusedInspector` через рабочий Unity MCP. Инструкция и примеры: `Tools/Context/inspector.md`. Начинай с одного объекта и фильтра компонента; отчёт не подтверждает игровой приёмки.

Перед выполнением задачи прочитай `lessons.md` и [PROJECT_MAP.md](PROJECT_MAP.md). Это основной справочник путей и систем проекта для каждого нового чата. Сначала выбери раздел механики, затем при необходимости открой связанный каталог `Docs/ProjectMap/*.md` и читай только нужные исходники по точным путям. Поиск внутри карты разрешён; обзор папок и поиск файлов по всему проекту по умолчанию не выполнять.

Карта заменяет обязательный запуск загрузчика и полное чтение `project.md`/`unity.md`. Исторические и профильные документы читать по необходимости; для моделирования также `blender.md`, для импорта — применимые правила `unity.md`. `Tools/Context/context.ps1 <тема>` остаётся необязательным помощником, когда нужны актуальные значения сохранённых конфигов.

При добавлении, удалении, переименовании файлов или изменении назначения механики обнови соответствующую тему в `Tools/Context/topics.json` и пересобери карту командой `python Tools/Context/update_project_map.py`. Не пересобирай её при каждом новом чате. Если путь отсутствует, проверь конкретный путь; если карта и ссылки не помогают, запроси разрешение на ограниченный поиск. Наличие файла не доказывает подключение к живой сцене.

Документация и ответы пользователю — по-русски; код, имена файлов и объектов — по-английски.
Выполняй задачу до сохранённого результата, пригодного для ручной проверки, в пределах доступных инструментов. Не заявляй об успешной проверке без фактического выполнения.
Сохраняй чужие изменения и Unity GUID. Перед правками проверяй текущую реализацию и затрагиваемые файлы без обязательного обращения к Git.
Коммиты и push разрешены только после явного подтверждения пользователя в чате для конкретных изменений; соблюдай раздел Git в `project.md`.

Эти четыре файла остаются рядом в корне репозитория. Для ИИ-клиента, который не читает AGENTS.md, пользователь должен явно указать прочитать этот файл либо подключить его через поддерживаемый механизм инструкций. Команды загрузчика описаны в `Tools/Context/README.md`.

Описание механизма Codex: https://developers.openai.com/codex/guides/agents-md.

## GameDev Hub (Координация, Задачи и Прямой доступ к Unity/Blender MCP)

GameDev Hub (`http://localhost:3888`) — единый центр управления проектом, архитектурными решениями (SSoT), очередью задач и синхронизацией команды через Radmin VPN.

### Главный архитектурный принцип: Никакого проксирования (Direct MCP)
**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО создавать цепочки вида `ИИ → MCP Hub → MCP Unity/Blender`.**
- Хаб **НЕ** является обёрткой или прокси для Unity или Blender.
- Агенты (Antigravity, Codex и др.) работают с **`unityMCP`** и **`blenderMCP`** **НАПРЯМУЮ через их родные инструменты**.
- Хаб используется **ИСКЛЮЧИТЕЛЬНО** для: получения контекста, блокировки задач, фиксации прогресса, регистрации багов и обсуждения механик в Дизайн-Лабе.

### Трёхфазный протокол работы агента:
1. **Фаза 1: Получение контекста из Хаба (SSoT)**
   - Перед написанием кода получи пакет контекста задачи: через MCP `gamedevHub.get_task_envelope(taskId)` или CLI `d:/projects/pirateslop hub/hub.bat task <taskId>`.
   - Заблокируй задачу за собой: `claim_task(taskId, agentName)` или `hub claim <taskId>`. Это предотвращает дублирование работы и синхронизирует статус с напарником через Radmin VPN.
   - Учитывай активные архитектурные решения (SSoT) и критерии приёмки из пакета.

2. **Фаза 2: Прямая реализация в Unity и Blender (Native Tools)**
   - **Для Unity**: вызывай родные инструменты `unityMCP` напрямую (манипуляции с GameObject, компонентами, сценами, запуск тестов, чтение консоли и прямое редактирование C# скриптов).
   - **Для Blender**: вызывай родные инструменты `blenderMCP` напрямую (`execute_blender_code`, генерация моделей, скриншоты вьюпорта, работа с ассетами).
   - Никаких промежуточных вызовов через Хаб в процессе технической работы с движком или 3D.

3. **Фаза 3: Передача информации и отчётность в Хаб**
   - **Во время реализации**: при завершении этапа или изменении ключевых файлов отправляй отчёт: `log_progress(taskId, message, diffFiles)` или `hub progress <taskId> <message>`. Это сразу отражается в AI Radar и ленте Хаба.
   - **После реализации**: вызови `propose_task_ready(taskId, testResults)` или `hub ready <taskId> [testResults]`. Задача перейдёт в статус `NEEDS_HUMAN_TEST` для ручной проверки разработчиком.
   - **При проектировании («Продумай механику...»)**: НЕ трогай код Unity. Сформируй спецификацию (плюсы, риски, подзадачи) и отправь в Дизайн-Лаб через `propose_design_dilemma` (или `hub propose <title> <desc>`). Дождись обсуждения людей.
   - **При обнаружении багов**: фиксируй их через `propose_bug` или `hub bug <title> <severity> <repro>`.

### Автоматическая обработка коротких фраз (Zero-Boilerplate)
Пользователь может отдавать краткие разговорные команды. Агент ОБЯЗАН сам вызывать соответствующие инструменты:
- **«Возьми задачу TASK-XXX [в работу]» / «Делай TASK-XXX»**:
  1. Вызови `claim_task(taskId)`
  2. Вызови `get_task_envelope(taskId)`
  3. Проверь требования и SSoT, кратко подтверди в чате и пиши код в Unity.
- **«Сдай задачу TASK-XXX» / «TASK-XXX готова» / «Отправь на проверку»**:
  1. Проверь компиляцию
  2. Вызови `propose_task_ready(taskId, "Тесты пройдены: [...]")`
- **«Придумай / спроектируй механику [...]»**:
  1. Не трогай код игры
  2. Вызови `propose_design_dilemma` с анализом плюсов и рисков в Design Lab.
- **«Проанализируй предложение LAB-XXX»**:
  1. Вызови `analyze_design_proposal(proposalId)`.
- **«Запиши баг [...]»**:
  1. Вызови `propose_bug`.
- **«Добавь в референсы [...]»**:
  1. Вызови `add_reference`.


## Создание 3D-моделей (Blender)

При запросе на создание новой 3D-модели в Blender обязательно создавай и используй двух субагентов:
1. **Арт-директор (Концепт)**: продумывает дизайн, генерирует 2-3 варианта 2D-референсов (с помощью инструмента generate_image) и составляет техническое задание для процедурной генерации (какие примитивы и модификаторы использовать). При генерации изображений указывай: отображать только саму деталь без лишних объектов, стиль ближе к low-poly (в стилистике корабля), на простом сером фоне, как будто это готовая модель во вьюпорте Blender.
2. **Моделлер (Blender/Python)**: пишет Python-скрипт для создания модели в Blender на основе ТЗ и самостоятельно исполняет его в открытом Blender через подключенный MCP сервер.

**Важно:** Перед написанием кода и фактическим созданием модели обязательно покажи пользователю сгенерированные 2D-референсы и дождись явного утверждения одного из них.

## Контроль качества по референсу (`visual_reviewer`)

Когда к задаче приложен референс (изображение от пользователя или утверждённый 2D-концепт):
1. После генерации изображения или создания модели в Blender вызывается субагент `visual_reviewer`.
2. Субагент через `view_file` сопоставляет референс и результат (скриншот вьюпорта Blender через `get_viewport_screenshot` или сгенерированный файл) по силуэту, пропорциям, ключевым деталям и стилю.
3. Если результат отличается, субагент возвращает статус `[NEEDS_REVISION]` со списком несоответствий и точечными инструкциями по исправлению, отправляя задачу исполнителю на доработку.
4. Задача передаётся пользователю только после статуса `[APPROVED]` от субагента либо при необходимости принципиального решения пользователя.

## Работа с VFX (Визуальные эффекты)

С 2026-10-08 пользователь поручил основному агенту самостоятельно выполнять VFX и удалить профиль `vfx_specialist`. Не создавать и не продолжать этого субагента. Основной агент проектирует, реализует и сохраняет эффект в согласованном объёме.

- Выполнять сложные эффекты по этапам пользователя. На тестовой карте сохраняется стена отдельных объёмных тёмных туч вокруг невидимой границы зоны, радиальная толщина 20 м. Последний разрешённый этап 2026-10-09 — ливень, мокрое дерево с плавным высыханием за 30 секунд, читаемый по расстоянию небесный фронт и фиолетовые молнии внутри стены с подсветкой соседних клубов и зависимым от расстояния громом.
- Уточнение 2026-10-09: видимые тучи начинаются минимум на 0.5 м выше максимального гребня текущих волн, с неровным округлым нижним краем. Невидимая граница зоны по-прежнему проходит от дна до высокого неба.
- Последующее уточнение 2026-10-09: верх видимых туч ограничен самой высокой геометрией игрового корабля плюс 10 м. Сужение и перекатывание туч к центру должны быть плавными, без перестановки узора по тикам; на паузе движение замирает. По окружности не должно быть одинаковых повторяющихся фрагментов объёма.
- Последнее уточнение 2026-10-09: отдельная туча теперь примерно 13–16 м вместо прежних 6–8 м. Требуется более плавный перекат и сильно тёмная грозовая масса с рельефом нескольких клубов, без вида гладких серых шаров. Толщина стены 20 м, высота и просвет над волнами сохраняются.
- Новое уточнение 2026-10-09: убрать дальнюю пиксельность и ближнее мыло, сделать движение самих клубов заметнее. Внутренний ветер может перекатывать тучи при фиксированном радиусе; пауза зоны сохраняет радиус и отключает урон. Солнце направлено к точке неба над центром карты; ясное небо и белые облака внутри круга плавно переходят в пасмурное небо и тёмные облака снаружи. Дождь и молнии всё ещё отключены; это уточнение расширяет текущий этап на небо.
- Последующее уточнение 2026-10-09: переход неба не должен выдавать круг или серую полосу при сужении; пасмурных облаков требуется меньше. Перекат меняет форму всей стены со всех сторон, включая верхние, боковые и нижние выступы, без неподвижного цилиндрического силуэта.
- Новое уточнение 2026-10-09: тучи не просвечивают сквозь воду. Добавить нижний перекрывающийся слой, чтобы низкие клубы проходили чуть ниже палубы; минимальный зазор теперь 0.2 м над максимальным гребнем вместо 0.5 м. Нижний край тоже неровный и меняет силуэт при перекате, как верхний; минимальный зазор не означает сплошную ровную линию. Не поднимать верх стены при добавлении нижних туч.
- Следующий этап 2026-10-09: сильный ливень идёт в облачной полосе и за ней, ограничивает дальнюю видимость, оставляет брызги/рябь на текущих волнах и брызги/мокрые следы на корабле; экранные капли преломляют изображение и стекают. Интенсивность и звук переходят плавно, под крышей новые экранные капли не появляются. Ресурсы и пулы готовить до входа в дождь. Сообщённый микрофриз не считать исправленным без измерения; сначала исключать загрузку звука, выделение ресурсов и компиляцию при пересечении границы. Только тестовый layout; молнии и waterline/spray сохраняют предыдущий выключенный режим.
- Учитывать мировые координаты, игровую камеру и геометрию карты. Сохранять чужие изменения, GUID, меню и остальные карты.
- Последнее уточнение 2026-10-09 заменяет прежний запрет молний только для тестового layout: вдали видны небольшие вспышки в массе туч, вблизи — ветвящиеся разряды и распространение фиолетового свечения по соседним тучам. Гром вдали не слышен, внутри стены громкий. Небесный фронт должен визуально помогать оценить расстояние до стены. Мокрые следы на дереве привязаны к реальному попаданию, поверхности и состоянию секции, живут отдельно от коротких брызг и плавно исчезают за 30 секунд. Микрофриз после первой предварительной загрузки остался; не выдавать следующую профилактику за измеренное исправление.
- Применять общий режим проверок: пользователь проверяет игру; не запускать Play Mode, сборки и замеры без прямого указания. Проверка компиляции не подтверждает внешний вид или FPS. Не присваивать эффекту статус визуальной приёмки без фактического просмотра.
- Последнее уточнение 2026-10-10 заменяет узкую стену туч на тёмный клубящийся дым во всём пространстве от края карты до текущего безопасного кольца. Максимальную высоту сохранять, движение должно плавно стелиться по воде; вдали виден изменяющийся фронт, внутри сам объём дыма ограничивает видимость игроков. Небо, молнии, ливень, мокрое дерево и экранные капли не менять. Только тестовая карта; прежние 20 м и отдельные тучи больше не являются устройством основного видимого объёма.
- Последующее уточнение 2026-10-10: первая дымовая версия отклонена как серая масса. Требуются полноценные объёмные движущиеся клубы у воды, сверху и с наружной стороны фронта в направлении безопасной зоны. Нижний зазор прежних туч не ограничивает дым; вода перекрывает его настоящей глубиной. Внутренний край и верх не должны образовывать ровную оболочку. Согласованные небо, молнии и дождь с эффектами по-прежнему сохранять.
- Последнее уточнение 2026-10-10: дымовая версия снова отклонена как чёрное полотно. Проверять фактический формат шумов: используемые Texture3D R8 содержат только канал r, другие каналы не дают формы/нормалей. Разрешены изменение распределения и частоты молний: разряды должны появляться по всей опасной площади и одновременно в разных местах перед кораблём. Сохранять ветви, фиолетовое рассеяние внутри дыма, затухание и зависимый от расстояния гром каждого разряда; новые вспышки не должны обрывать активные. Небо, ливень, мокрые следы и экранные капли не менять. Только тестовая карта.
- Последующее уточнение 2026-10-10: пользователь видит неподвижный дым издалека и вблизи, слабую плотность и резкую серую границу при входе. Движение самого трёхмерного поля и силуэта должно быть заметным; плотность наращивать непрерывно по глубине. В тестовой дымовой области отдельную равномерную серую пелену RainScreen исключить: ограничение видимости даёт объём дыма. Это исключение касается только дублирующей пелены, не капель, брызг, мокрых следов, звука, неба или молний.
- Последнее уточнение 2026-10-10: дым выглядит треугольными складками и слабо клубится; внутри нужны около 10 м плохой видимости без полностью чистых дыр. Проверять ограничения старой узкой стены: они не должны отсекать заполненную опасную область.
